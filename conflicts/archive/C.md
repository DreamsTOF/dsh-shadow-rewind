# 冲突组 C —— 「删除」被两套机制处理成两个结果（决策文档）

> 冲突描述：卷一冲突组 C（词法删除「无 hunk、仅展示」vs 检查点 fs 删除
> 「可完整撤销」，产品层画成同一种「已删除」）。
> 附带事实：词法解析器对 bash 反斜杠转义不识别（`deleted-paths.ts:67-79,88-92`），
> `rm my\ file.txt` 会展示成错误路径；反引号守卫（:154）会把 PowerShell 的
> 合法整段丢弃。这条管线本身的解析质量就有限。

## 前提

A-2（挂靠）落地后，C 的两个方案其实是同一件事的两步：fs 条目成为删除的
唯一权威，词法条目只剩「fs 证据未就绪时的占位」一个角色。

## 方案 C-1：词法删除降级为 fs 证据的占位 ★推荐

- **做法**：`deleted: true, diffs: []` 的词法条目只在 fs 管线尚未给出该路径
  证据时显示（标注「待确认」类文案）；fs 条目一出现即顶替并解锁撤销。
- **改动面**：客户端占位生命周期（live-bar / ProducedFiles / FileReviewTab
  三处的合并优先级）+ 降级文案。
- **代价**：小。fs 缺失（历史轮/配额淘汰）时删除退回只读展示——与现状的
  不可撤销一致，不是退化。
- **顺带**：词法误报（反斜杠切分错误、PowerShell 反引号漏报）造成的假删除
  行会被 fs 证据修正或超时消失，解析质量差的影响被限制在「短暂占位」内。

## 方案 C-2：直接删掉词法删除管线

- **做法**：删 `deleted-paths.ts` 及其在 turn-deliverables / session-changes
  的两个消费点。
- **代价**：终端删除在 fs 证据到位前（live 轮、fs-changes 未 warm、历史轮）
  完全不可见；闸开时 fs 端点本就剔除了部分路径，可见性进一步收窄。
- **收益**：实现最简，且解析器分支差异（bash/PowerShell）问题整段消失。
- **诚实评估**：自用下「删除晚一拍出现」大概率可接受；真正的损失是 fs-changes
  端点故障时的兜底显示。选它还是 C-1，取决于你对 live 轮删除可见性的要求。

## 方案 C-3：维持现状

「删除」永远有两个互相矛盾的真值，词法误报直接进 UI。

## 推荐

先 C-1；若 A-2 之后占位逻辑仍觉得碍事，退 C-2。
