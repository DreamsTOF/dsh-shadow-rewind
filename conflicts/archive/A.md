# 冲突组 A —— 「轮变更」被两套数学各算一遍（决策文档）

> 冲突描述：卷一冲突组 A（工具视图 hunks vs 检查点整树 diff）。
> 这是全插件的结构性根因，C、E、I、J 四组的大部分问题跟着它走。

## 方案 A-1：文件广播器（完整版）

你的提案的完整形态：宿主侧一个进程内事件总线，所有**在写入瞬间就能知道
path 的写入路径**发布事件，清单与归属从事件流统一推导。

- **设计**：新模块 `src/file-bus.ts`（约 150 行，per-workspace 订阅即可）。
  事件形状 `{cwd, path, at, writer: {sessionId, kind: 'tool'|'run_code', callId}, seq?}`。
- **发布点**（都是现成的挂载位置，不是新观测）：
  1. write / edit / str_replace_editor 的 post-execute——`host.ts` 录制器已经在
     这里拿到 `{path, before, after}`，顺手 emit；
  2. run_code 录制器逐 path emit。
- **消费**：fs-changes 的每个 fs 条目按三级标注写入者——事件命中 → 直接挂；
  仅命中命令窗口 → 终端归因（沿用 command-windows）；都无 → external。
  客户端卡片/侧栏/live 条只消费 fs 条目这一份清单。
- **诚实边界**（不夸大）：终端命令与外部进程在写入瞬间拿不到 path 和内容——
  这正是当初引入检查点对比的原因。所以广播器统一的是**归属与清单**，
  内容来源仍是检查点 diff。外部编辑器永远无事件（README 已声明的闸边界，不变）。
- **代价**：本清单中最大的结构性改动（大）。成本集中在客户端三个消费点的
  切源与混沌套件回归；服务端逻辑反而变简单（快照归属网格只剩终端写入一种用途）。
- **顺带解决**：C（删除占位→fs 证据顶替有单一来源）、E（录制器降级为事件源）、
  I 的大半（归属在写入时刻已定，不再事后反推）、J 的清单分叉。

## 方案 A-2：广播器的最小实现——不新建模块，先做「挂靠」★推荐先行

- **做法**：`computeTurnFsChanges` 里对每个 fs diff path，先查本轮工具侧已
  有的路径记录（host.ts 录制器结果 + 工具结果 hunks），命中即直接标注写入者；
  未命中再走命令窗口；都无 → external。工具条目从客户端清单退役（diff 内容
  预览按需仍可取自工具 hunks，或直接全走 fs 按需拉取）。
- **代价**：小到中。`rewind-host.ts` 一个函数的归属逻辑改造 + 客户端合并层
  **删代码**为主（三处「工具优先、fs 跳过」规则直接消失）。约拿到 A-1 的
  80% 收益（A/C/E/I 的根因），无新模块、无事件协议。
- **与 A-1 的关系**：A-2 是 A-1 的第一步。挂靠逻辑写成一个纯函数后，A-1
  只是把它的输入从「事后查录制」换成「事件推送」，迁移无浪费。live 条实时性
  在 A-2 下不变（仍靠 warm 轮询），这是 A-1 相对 A-2 的唯一实质增量。

## 方案 A-3：对账式双轨（卷一 A2）

- **做法**：保留两套清单，客户端同路径做内容对账，相等才跳过、不等标冲突。
- **代价**：中。「不等」分支的产品语义要定义（显示谁、撤销谁），且 CRLF/
  大文件/快照损坏都会涌进对账分支——长期维护成本最高的选项。I 组的归属
  问题原样保留。仅当你在意「工具 hunks 秒开、不等轮末快照」这个体验才考虑。

## 方案 A-4：维持现状

- 同一条目最多 5 种互相矛盾的呈现（两套清单 × 三套可逆判定，见 F1+H1）。

## 推荐

A-2 先行；用一段时间后若需要 live 实时流或事件持久化，再升 A-1。
C、E、I-1/I-3、J-1/J-2/J-3 的方案默认以 A-2 为前提书写。
